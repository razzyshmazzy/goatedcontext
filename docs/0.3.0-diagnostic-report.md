> migration-list parameter for fault injection). Every claim below links to a test

# Executive Summary

- **There is NO application-level cache anywhere in the retrieval path.** Every
  `retrieve()` re-reads the whole DB and recomputes. Repeated-query speed is purely
  SQLite/OS page cache, confirmed by **warm ≈ cold** at every size (e.g. 10k: cold
  122 ms vs warm median 124 ms). This is a correctness *virtue* (never stale,
  cross-process fresh) and a performance *cost*.
- **The real scaling bottleneck is `O(total preferences)` recompute per call**, not
  fetching: `RetrievalEngine.candidates()` calls `prefs.list()` = `SELECT * FROM
  preferences` and filters scope/status in JS, then builds IDF + scores the whole
  relevant pool. 50k prefs → **~560 ms per retrieval**, and the prompt hook runs this
  on **every prompt**.
- **The strongest 0.3.0 win is SQL-side candidate filtering, not caching.** It cuts
  the many-repo case to `O(globals + this-repo)` with zero freshness risk.
- **One P1-ish correctness-of-delivery finding:** the `always`/`conditional` delivery
  caps (20 each) silently drop matching rules beyond 20, with an **age/id** tiebreak
  rather than importance.
- **No P0 found.** Corruption is handled safely (no auto-reset / no data loss),
  secrets never leak, concurrency is robust (no lost writes, dedup storm → 1 row,
  cross-process freshness), migrations are atomic.
- **Gemini scorecard:** right about secret isolation gaps and backup feasibility;
  wrong about connection pooling (unjustified) and the lexical prefilter (unsafe).

# Current Architecture Observed

```
CtxContext.open(env)            one process = one SQLite connection (closed on exit)
  openDatabase(paths)           WAL, busy_timeout=10000, synchronous=NORMAL, foreign_keys=ON
  services: preferences / repos / environments / events / stats / retrieval

retrieve(opts):
  repo = repos.resolve(cwd)         # git subprocess x2 (toplevel + origin), NO timeout
  withReadTx(BEGIN DEFERRED):
    candidates = prefs.list()       # SELECT * FROM preferences  (ALL rows) + JS filter
    split always / conditional / relevant
    conditional: evaluateCondition() per row   (glob for file leaves)
    relevant:    buildIdf(all candidates) + score each     (O(candidates))
    resolveConflicts(all)           # precedence + exclusive-domain/subject dedup
    cap: keptAlways≤20, keptConditional≤20, keptRelevant≤limit(≤15)
  markUsed() only when track!==false  (hook passes track:false → pure read)

statements: re-prepared on every db.query() call (no statement cache)
```

Static projection (`selectStaticPreferences`) and `exportData` also call
`prefs.list()` (full scan) and filter in JS.

# Retrieval Scaling

`scripts/bench/diagnostics.ts` (in-memory DB = pure compute, no page-cache confound):

| prefs | active candidates | cold ms | warm median | warm p95 | warm p99 | result count |
|------:|------:|------:|------:|------:|------:|------:|
| 1,000 | 811 | 20.6 | 15.3 | 17.9 | 19.1 | 45 |
| 10,000 | 8,054 | 122–131 | 124–126 | 131–133 | 135–140 | 52 |
| 50,000 | 40,092 | 536 | 562 | 585 | 586 | 52 |

**Warm ≈ cold at every size** → no app memoization. Growth ≈ linear in active
candidate count (1k→10k ≈ 8×; 10k→50k ≈ 4.5×). Cost is dominated by
`list()` row-mapping + `buildIdf` + per-candidate scoring + `resolveConflicts`, all
`O(candidates)`. Complexity verdict: **~O(n), dominated by JS string/token work over
all candidates, not by SQL and not by condition evaluation.**

# Repeated Query Behavior

Running the identical query 1/10/100/1000× yields no speedup beyond the first
(SQLite/OS) warm-up — warm median ≈ cold at 10k (124 ms vs 122 ms). `scale-retrieval`
asserts a retrieval is **byte-identical across 100 runs** (determinism / cache oracle
baseline). Changing `languages` for the same task text changes the result set
(`prefilter-experiment`), so any task-only memo key would be unsafe.

---

# Cache Invalidation Findings

With no cache, "invalidation" = *does the next read see the write?* All proven live
(`freshness-invalidation`): ADD, FORGET, APPROVE→appears, REJECT→disappears, and a
NEGATIVE case (a query that matched nothing picks up a newly-added matching rule). If
0.3.0 adds a cache, these tests become its mandatory invalidation guard.

# Cross-Process Freshness

`freshness-invalidation` spawns **real processes**: A reads (miss) → B
`ctx remember` → A reads again in a fresh process → **sees the write**. Each process
opens its own connection; WAL makes the commit immediately visible. No process-lifetime
cache blocks this.

# Many-Repo Findings

`scale-many-repo` (10k prefs across 100 repos): repo-scoped retrieval returns the
repo's rows + globals and **never another repo's** repo-scoped rules; a non-git cwd
sees only globals; opposite exclusive-domain rules in two repos never bleed across.
**Caveat (perf, not correctness):** isolation is enforced in JS *after* loading all
rows, so a 100-repo store still scans every row per retrieval.

# SQLite Concurrency

`concurrency-processes` (real OS processes):
- **32 readers** → all exit 0, valid JSON, **identical snapshot**, zero lock errors.
- **24 readers + 6 writers + 4 stats-hooks** → no corruption, no lock errors, exactly
  **6** distinct writes persisted (no lost/dup writes), readers' JSON well-formed.
- **12-way dedup write storm** (same `propose`) → exactly **1** preference; all 12
  processes exit 0 (BEGIN IMMEDIATE + `ON CONFLICT` + unique dedup index).
- `stats-history`: **20 concurrent hook processes → hook_runs == 20** (file-lock loses
  no increments).

# WAL / Busy Timeout Findings

`wal-audit` pins the live settings: `journal_mode=wal`, `busy_timeout=10000`,
`synchronous=1 (NORMAL)`, `foreign_keys=1`. Reopening an already-migrated DB keeps WAL
with no re-migration churn. Under the tested concurrency these defaults produced **zero
`SQLITE_BUSY`/"database is locked"**. Recommendation: **leave as-is.**

# Connection Pooling Verdict

**Not justified.** DB reopen (steady state) median **1.6 ms** vs. process startup
**~60 ms** (`ctx --version`). CLI processes are short-lived and single-connection; the
open cost is noise against Node startup. There is no persistent-process path that would
amortize a pool. Pooling would add lifecycle complexity for ~1 ms. **Do not add.**

# Similarity Bottleneck Analysis

`JaccardSimilarity` is used only for **propose dedup**, not retrieval scoring.
Retrieval relevance uses `buildIdf` + token overlap + domain/category bumps, all
`O(candidates)`. The dominant cost at scale is iterating + tokenizing **every** active
candidate, because candidate selection isn't pushed into SQL. (Secondary: the stemmer
is inconsistent — `"table"→"table"` but `"tables"→"tabl"` — see `prefilter-experiment`.)

# Lexical Prefilter Experiment

**UNSAFE — do not implement.** `prefilter-experiment` proves a "share ≥1 subject token
with the task" prefilter drops a preference the engine correctly returns: the engine
scores a rule over threshold on a **domain match alone** (`W_DOMAIN=0.5 ≥ 0.25`) with
zero shared tokens. A naive prefilter false-negatives it. Safety would further depend
on phrasing (stemmer `table`/`tables` mismatch). Recall cannot be guaranteed.

# Memory Growth

No process-level unbounded maps exist (no per-query cache, no key accumulation). A
1M-char task retrieves in well under the 5 s catastrophic bound (`large-prompt`), with
no quadratic/ReDoS blowup (polarity regex is linear; tokenization is `O(n)`), and the
task text is **never persisted** to prefs/history/stats.

# Migration Atomicity

`migration-atomicity`: all shipped migrations apply to v5; a migration that throws
leaves the schema at the **last good version** (no partial advance), rolls back
intra-migration statements (failed `CREATE` is gone), leaves the DB readable, and a
fixed re-run **resumes** idempotently. Underlying primitive `withWriteTx` rolls back all
writes on throw. **Solid — no rewrite needed.**

# Backup Strategy Experiment

`backup-experiment`: `VACUUM INTO '<file>'` produces a consistent standalone snapshot
with identical row counts and `integrity_check = ok`, leaves the source untouched, and
**succeeds while another connection holds an open read snapshot** (WAL). It is plain SQL
(works on both `node:sqlite` and `bun:sqlite`), no API divergence. **If 0.3.0 wants a
pre-migration safety net, `VACUUM INTO` is the recommended strategy** (no new deps).

# Secret Backend Findings

`secret-audit`: secret values never appear in **export** (environments excluded
entirely), the **hook block** (only env *names*), **doctor** output, or
**stats/history**. `FileSecretStore.describe().secure === false` and says "same
machine" — **honest**, never a fake-secure claim. Backend selection is explicit:
`file` forced works everywhere; `auto` uses DPAPI on Windows when available else
encrypted-file; forcing `dpapi` on an unavailable host **throws** rather than silently
downgrading. **Gap (Gemini was right):** on macOS/Linux there is no OS-keychain backend
yet — the fallback is encrypted-file with the key beside the data. Reported, not fixed.

# Adapter Extensibility Findings

`adapter-extensibility`: every agent exposes a complete boolean capability profile and
all can host the memory skill; delivery routing is fully determined by the capability
object (static/runtime/unsupported partition verified per agent). The shared primitives
(`skill-install`, `planDelivery`, `managed-block`, `memory-protocol`) are **agent-neutral
and reusable with zero core edits**.

# Fake Fourth-Agent Exercise

A test-only fourth agent, assembled **only** from shared primitives, installs / repairs
(idempotent) / detects-stale / uninstalls its memory skill and projects a managed static
block — **no core changes needed to reuse the engine**. What a *first-class* new agent
still forces (friction, not pain): `capabilities.ts` (AgentId union + `capabilitiesFor`
switch), `registry.ts` (`LABELS`, `STATUS_FNS`, a `<agent>Status()`), `cli/index.ts`
(install/uninstall/repair/agents branches), `cli/setup.ts` (auto-detect). Verdict:
**mildly repetitive, not structurally painful.** A `BaseAdapterInstaller` would remove
~4 touch-points but is cosmetic — **low priority**.

# Skill Generation Findings

`skill-parity` (+ existing `memory-protocol`/`command-invocation`): committed
`skills/*/SKILL.md` match the generator exactly (no drift); Claude/Codex/Cursor bodies
are byte-identical on a platform; only the Windows `ctx.cmd` invocation note differs,
and stripping it yields the POSIX body byte-for-byte; the staleness marker is present in
every render. **No policy drift.**

# Export / Import Scale

`export-import-scale` (2k unique prefs): export→import into a fresh store is **lossless**
(scope/status/applicability/condition distribution preserved exactly; conditional⇔
condition invariant holds). Re-import is **idempotent** (0 new rows; duplicates
collapse). No secret material in the bundle; repos linked by stable identity, not local
ids. **Perf (bench, 10k):** export **107 ms**, import **982 ms** — import is ~10× export
because `importOne` runs **one transaction per preference** (N+1). Export itself issues
one evidence query per preference (N+1). Both are correctness-safe but a scale cost.

# Startup Latency

`scripts/bench/diagnostics.ts` (real processes, cold):

| command | median ms | p95 ms |
|---|---:|---:|
| `--version` | 64 | 65 |
| `prefs --json` | 70 | 73 |
| `get` | 121 | 168 |
| `doctor --json` | 112 | 112 |
| `agents --json` | 141 | 150 |
| `hook codex-prompt` | 101 | 127 |

Breakdown: ~60 ms Node startup + bundle parse is the floor; DB open adds **1.6 ms**;
`get`/`hook` add retrieval + **2 git subprocess spawns**. Since agents invoke `ctx`
per prompt, the **git spawns + O(n) retrieval** are the latency levers, not DB open.

# Security / Failure-Mode Findings

- **Corrupt DB → fail safe, no data loss.** `corruption-recovery`: doctor reports a
  corrupt DB as a failure with a fix; the CLI **does not overwrite/reset** a corrupt
  `ctx.db` (bytes preserved); a missing parent dir is created on write; truncated/empty
  files are reported, not silently repopulated.
- **No destructive auto-reset anywhere.**
- **Injection hardening:** `sanitizeInjectedText` escapes angle brackets, flattens
  newlines/control chars, collapses whitespace, caps a value at 500 chars (a 100k-char
  rule contributes <500 chars to the block). `large-prompt` verifies structural-breakout
  neutralization.

| ID | Sev | Finding | Evidence |
|---|---|---|---|
| D1 | **P1** | `always`/`conditional` delivery caps (20 each) silently drop matching rules beyond 20; the surviving set is chosen by **precedence→createdAt→id**, so among equal-precedence rules it is effectively arbitrary (newest-written lose). # 0.3.0 Recommendations (ranked by measured evidence)

1. **Rework the always/conditional cap selection (D1, P1).** Collapse identical
   always-rules before counting; when capping equal-precedence rules, prefer a stable
   importance signal over write-age; consider raising/condition-scoping the cap.
   *Why:* silently drops user-authored always rules.
2. **Push candidate selection into SQL (D2, P2) — the single biggest win, cache-free.**
   Replace `prefs.list()`+JS filter in `candidates()`/projection with
   `WHERE status IN (…) AND (scope='global' OR repo_id=?)` and only load/score what can
   match. Cuts the many-repo + large-store hook latency without any freshness risk.
   *Measured:* 50k retrieval 536–562 ms today.
3. **Add a timeout to hot-path git subprocesses (D3, P2).** Bound `gitToplevel`/
   `gitOriginUrl`; on timeout, behave as "no repo" (the hook already fails open).
4. **Do NOT add an application retrieval cache.** The bottleneck is compute, not fetch;
   a cache adds cross-process staleness risk (freshness tests show reads must be live)
   and the warm≈cold data shows re-fetch is not the cost. If ever added, gate it behind
   the existing `freshness-invalidation` tests.
5. **Do NOT add connection pooling** (open 1.6 ms « startup 60 ms).
6. **Do NOT add the lexical prefilter** (proven to drop domain-only matches).
7. **Optional:** batch `importOne` into one transaction (D5); prepared-statement reuse
   if a profile justifies it; `VACUUM INTO` pre-migration snapshot (validated safe).
8. **Defer:** `BaseAdapterInstaller` (cosmetic), macOS/Linux OS-keychain secret backends
   (real gap, but file fallback is honest today).

### What Gemini was right about
- **Secret isolation** is a genuine cross-platform gap (no OS keychain off Windows).
- **Backups** are feasible and safe under WAL (`VACUUM INTO`).

### What Gemini was wrong about
- **Connection pooling** — unjustified for short-lived single-connection CLIs.
- **Lexical token prefilter** — unsafe; drops domain/category-only relevance matches.
- (Implicit) **caching** — would not address the real `O(n)` compute cost and would
  introduce freshness/cross-process-staleness risk.

### Suggested 0.3.0 implementation order
1. D1 cap rework (correctness).  2. D2 SQL-side candidate filtering (scaling).
3. D3 git timeout (robustness).  4. (optional) import batching, statement reuse,
`VACUUM INTO` backup.  5. (defer) adapter base class, secret backends.

# 0.3.0 Implementation Outcome (before → after)

The three evidence-backed fixes were implemented. Production source changed:
`retrieval.ts` (D1 + delivery budget), `preferences/service.ts` (D2 `listCandidates`,
D5 `importMany`), `project/projection.ts` (D2 route), `utils/git.ts` + `repos/repo.ts`
+ `cli/index.ts` (D3 timeout + probe), `storage/sqlite/migrations.ts` (v6 index).

## D1 — delivery caps removed (P1 → fixed)

`MAX_ALWAYS`/`MAX_CONDITIONAL` (20 each) are gone. Every effective `always` + matched
`conditional` rule is now delivered; `relevant` keeps its relevance top-K. Omission is
only ever via an **explicit** `DeliveryBudget` (default unlimited) and is reported in a
new, always-present `delivery` block (`matched`/`effective`/`delivered`/
`omittedByRelevanceLimit`/`omittedByBudget`). Regression matrix:
`tests/delivery-semantics.test.ts` (21/100 always, 21/100 conditional, mixed,
conflicts & repo-precedence among >20, locked-before-approved, determinism, exact
budget omitted-set), plus the rewritten `scale-retrieval`/`applicability`/
`conditional-retrieval` cases.

| case | before (0.2.x) | after (0.3.0) |
|---|---|---|
| 40 matching global always | 20 delivered, 20 silently dropped | **40 delivered** |
| 100 matching always | 20 | **100** |
| 40 matching conditional | 20 | **40** |
| survivor selection | precedence→**createdAt**→id (age-biased) | full set; order deterministic, nothing dropped |

## D2 — SQL candidate reduction (P2 → fixed, cache-free)

`candidates()` and the AGENTS.md projection now call
`PreferenceService.listCandidates()`, which filters status + scope/repo in SQLite via
two targeted `UNION ALL` branches. EXPLAIN QUERY PLAN confirms the repo branch seeks
`idx_prefs_repo (repo_id=?)` — other repos' rows are never scanned — using **existing
indexes (no schema change for D2)**. Semantic parity vs the old `list()`+JS-filter
path is proven deeply equal at 100 / 1k / 10k (`tests/d2-candidate-oracle.test.ts`,
4150 assertions).

Many-repo store (100 repos), one repo's retrieval (`scripts/bench/diagnostics.ts`,
in-memory = pure compute):

| prefs | rows loaded before | rows loaded after | reduction | candidate build before→after | full retrieve |
|------:|------:|------:|------:|---|---:|
| 10,002 | 10,002 | 4,015 | **−59.9%** | 110 ms → **45 ms** (2.3×) | 74 ms |
| 50,002 | 50,002 | 20,129 | **−59.7%** | 457 ms → **199 ms** (2.3×) | 316 ms |

No-repo/global retrieval also improved (loads only global-active rows): 50k warm
**≈560 ms → ≈290 ms**. No cache, no pool, no prefilter were added.

## D3 — git timeout + request-local reuse (P2 → fixed)

All git subprocesses run under a 5 s hard timeout (`GIT_TIMEOUT_MS`; internal
`CTX_GIT_TIMEOUT_MS`/`CTX_GIT_BIN` test seams). On timeout the child is killed and the
call fails safe to the existing fallback (null → no repo / no remote → deterministic
path identity). A request-local `GitProbe` memoizes repo-root/origin per invocation
(detect-then-resolve now spawns git twice, not four times). Tests:
`tests/git-timeout.test.ts` (real timeout killed near 300 ms not 4 s; repo-root vs
remote timeout fallback; no-repo; malformed output; reuse count 2-vs-4; real git still
works).

## D5 — import batching + dedup index (P3 → fixed)

`importData` now imports in **one transaction** (`importMany`), and migration **v6**
adds a general `idx_prefs_dedup` index (the v2 one is partial: proposed/observed only),
so the per-record dedup lookup is an index seek instead of a full scan. This removes
the import's O(n²) behavior:

| op (10k) | before | after |
|---|---:|---:|
| import | ~982–1082 ms | **~421 ms** (2.4×) |
| export | ~107–130 ms | ~130–150 ms (unchanged; N+1 evidence queries remain) |

## Deferred (unchanged, by design)

- **Pre-migration backup (§22).** `VACUUM INTO` is validated safe
  (`backup-experiment`) but auto-backup-on-migration (trigger policy, bounded backup
  count, failure handling) adds migration-path complexity for a rare event → deferred
  to 0.3.x.
- **macOS/Linux OS-keychain backends**, **`BaseAdapterInstaller`**, **export N+1** —
  deferred as before (real but non-blocking; file-secret fallback stays honest).

## Policy confirmations

No retrieval/similarity/candidate cache added; no connection pool; no lexical
prefilter; DB pragmas (WAL, busy_timeout=10000, synchronous=NORMAL, foreign_keys=ON)
unchanged; migration framework used for the one additive index; adapter registry
untouched.
